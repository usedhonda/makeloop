# Codex launch surface

Read for Step 4/6 on Codex only. Use native capabilities actually exposed in this session.
Official documentation or an installed CLI version alone does not establish session availability.
Unconfirmed/unavailable features belong in Conditional options without runnable copy fences.
Choose from the requested work, not whether the user named a runtime. A completion request
keeps completion intent; ordinary no-Goal execution can pursue successive necessary steps now
without promising cross-turn persistence. Only an explicitly selected bounded pass stops after one unit. A blocked goal backend with no exposed resume/active operation remains unavailable;
never invent that operation, reset its state/budget or silently replace it with a manual tick.
Classify limits by source/enforcement as in the output guide; an internal count is not exhausted
user authority and replanning it cannot restore a missing native control.

| Need | Candidate | Explanation |
| --- | --- | --- |
| Finish scoped work in the current execution | Ordinary no-Goal message | Follows successive necessary steps; no native cross-turn setup |
| Explicitly try one bounded iteration | Manual tick | First inspect the changes and evidence; returns control after one iteration |
| Pursue a closed goal across turns | `/goal` if available | Same contract/state and objective; no permission expansion |
| Revisit a watcher in the same chat | Chat scheduled task if available | Uses this chat's context; setup is distinct from one tick |
| Independent background observations | Project/standalone scheduled task if available | Explain local directory versus isolated worktree and state visibility |
| CI/external scheduler | `codex exec resume` | Bind the exact session and working directory; no runner is created |

For closed completion work, include a ready Goal-equipped launch in the initial proposal when
native Goal is available; do not wait for the user to ask a second time. Recommend it when the
request is to keep looping/continue until completion. Ordinary execution can be an alternative,
but is not an equivalent cross-turn loop. No-Goal is not synonymous with one iteration.
Preserve an explicit goal/cadence/CI choice rather than forcing manual mode. A confirmed explicit CI/external-resume choice remains selected and
recommended in the contract, INDEX and final launch group; manual is only an optional alternative. Describe the purpose, behavior, effects, check, stop and resume for each
candidate using the shared output guide. No fake `/loop`, `/ralph-loop` or `codex-loop` commands.

## Final copy choices

Use a short explanation, then end with **貼り付けるプロンプトはこれです** (localized to the user).
Label each complete code block with its mode and actual input destination. Saved design paths
are references, not the paste text; a bare resume control does not replace the task-bound prompt.

Use the shared output guide: save/check first, then explanations, the saved contract path (full
body only on explicit request), and, for ready proposals only, one final launch group with A/B/C labels. Name the actual paste surface: **Codex CLI input**, the
**Codex desktop chat**, or the **IDE chat** for `text`; the **OS terminal** for `sh`.
For closed completion work, include native Goal from the first proposal after the binding below.
When no other runtime is explicitly selected and both modes are ready, pair recommended Goal
completion with ordinary current-execution completion, using the same contract/state and
REMEDIATION SCOPE. An explicit no-Goal or bounded-pass request still wins.
An open watcher gets one tick plus a supported schedule
setup only when appropriate; label setup as creating a schedule, not as one observation.
Offer `codex exec resume` only for the explicit CI/external intent below; it is a terminal command,
not a slash command. Do not infer desktop/IDE capabilities from CLI help or offer a fake `/loop`.
Put the recommended choice first, preserve explicit supported mode choices, and make each block
complete with the exact contract/state and execution unit. Emit slash launches as one physical line.

## Launch forms

Render with actual paths and values in the user's language; these are illustrative scaffolds.

- Ordinary closed message: “Follow .loop/repair.md through its required work and verification.”
  Bind outcome, provisional pending work, delivery/review and actual stop conditions in the contract.
- Explicit bounded-pass message: “Follow .loop/repair.md for exactly one iteration.” Bind state,
  criteria, reporting and limits in that saved contract, not a long launch message.
- Open manual message: “Follow .loop/deploy-watch.md for one watcher tick.” Bind the cursor,
  trigger, permissions and stopping in the saved contract.
- Goal: `/goal Complete the original outcome in .loop/repair.md under its saved execution and verification rules.`
  Save detailed scope, recovery, limits, requested pause and state/resume handling in that contract.
  Retain native budget/setup arguments when actually required by the host; do not put non-success
  exits in its success rule or omit a genuine native prerequisite merely to shorten the text.
  Before a blocked decision, diagnose the impediment, repair it or use an authorized productive
  alternative when possible, and return to original work. If that remediation assessment proves
  no productive authorized repair/alternative or independent work remains, save an incomplete checkpoint with the
  waiting condition and use only actually available host stop/pause controls. Do not mark the
  native goal complete merely because a wait checkpoint was saved.
- Chat schedule setup message: “Create a scheduled task in this chat, every five minutes,
  running one tick of .loop/deploy-watch.md with .loop/deploy-watch.cursor.json; observe only
  new events and stop under the contract's conditions.” Label it **schedule setup**, not a tick.

For external orchestration, show a shell command only when the request mentions CI/cron/wrapper
and the exact existing session ID and working directory are known. Verify installed help before
selecting flags. Use `codex exec resume SESSION_ID PROMPT` with real resolved arguments, proper
shell quoting, and explicit working-directory binding. Do not use `--last` for an unattended loop:
the most recent conversation can belong to another purpose. If the ID is unknown, explain what
is missing. A manual message is a separate optional mode, not an equivalent replacement for
requested continuation; keep it unselected unless the user chooses it. JSONL/output-schema options
are optional integration aids, not a new runner or proof of task success.

## Continuation and scheduling boundaries

### Bind a fresh Goal during generation

Not configured/not started is the normal status of a ready proposal, not a capability failure.
Assess the intended execution surface separately from the generator's tool list. A confirmed
target CLI `/goal` surface and its lifecycle controls, recorded in a host-bound capability profile
or direct target observation, suffice even when the generator cannot invoke create/read/update
itself. Do not infer target capability from a version or generic documentation alone. Inspect
current target Goal state using available read-only evidence; do not create a Goal as a probe.
With no unfinished Goal and confirmed target start/lifecycle controls, bind the lifecycle
below in the saved contract now. Name the target and evidence, and require the executor to recheck
current state/ownership before starting. Do not defer this assembly as "stop conditions need connecting"
or put an otherwise ready Goal in Conditional options merely because it has not been started.
On a CLI with a confirmed `/goal` input surface, render the native slash launch. On other hosts
with exposed Goal tools but no confirmed slash surface, render a normal setup prompt explicitly
instructing the executor to create the saved objective with `create_goal`, then execute it
(for example, `Use create_goal for the objective in .loop/repair.md, then execute it.`
or the language-neutral prefix `create_goal: .loop/repair.md` followed by the setup instruction);
that is a Goal setup proposal, not an ordinary "continue" sentence. Generation itself does neither.

- Start: the chosen launch activates the original objective once. Preserve the existing state;
  do not replace an unrelated unfinished Goal. Inspect an existing matching Goal before reuse;
  a blocked/paused Goal needs its actual supported resume control, not fresh creation/reset.
- Continue: pursue successive necessary in-scope actions and real verification. A checkpoint,
  one green subset, one completed step or a final chat message is not completion of the Goal.
- Recover: classify the first failure, perform necessary authorized repairs under REMEDIATION
  SCOPE and verify their effects before returning to original work in the same Goal. Repair is
  goal work, not merely independent work; do not require the user to request it a second time.
- Complete: call `update_goal(status="complete")` only after all original requirements and
  required delivery/review have current evidence; report the returned status.
- Pause: only an explicit user pause request/condition authorizes `paused`. Bind such a supplied
  condition to `update_goal(status="paused")`; do not invent a review pause for an ordinary loop.
- Block: record the impediment promptly, not an automatic status change. A terminal blocker
  requires evidence that necessary authorized repair/alternatives and independent safe work
  cannot make progress. Keep diagnosis, attempted repairs or concrete boundary reasons, remaining
  work and the unblock condition in existing state. Do not require unsafe trial actions.
  Use `blocked` only under the exposed tool's actual recurrence/impasse rule. If it requires three consecutive
  goal turns, let genuine native continuations establish those turns; never fabricate them.
  A blocked checkpoint remains incomplete. Do not require immediate pause permission for
  every hypothetical future blocker before offering a fresh Goal.
- Limits: preserve actual user/platform limits and let native budget enforcement apply. Supply
  a token budget only when explicitly requested; internal progress checkpoints do not terminate.

Keep concrete unsupported user-requested pause behavior, exhausted hard budgets and actual owner
conflicts conditional. Missing lifecycle wording in a draft is repairable generation work, not
evidence that the native runtime is unavailable. Show ready / not configured / not started together.

- Generated contract, configured goal/schedule, started run and finished run are different states.
  FINAL/ITERATING are contract reports, not proof of native achieved/cancelled/exited state.
- For an explicitly requested pause point, offer native goal continuation only when the exposed
  controls can honor that user-authorized pause. If `update_goal` accepts `paused` in this session,
  bind the request/condition, call it only at that boundary and report the returned status; never
  use `complete` or invent `blocked` to make an unfinished goal stop. A later explicit resume
  releases that reached pause, not the remaining review/approval or cumulative limits.
  Otherwise keep the requested mode unconfigured and explain a bounded manual pass as a separate
  optional mode, not a selected replacement; no runnable substitute before that choice.
  explain the user's `/goal pause` control without claiming to have invoked it. Do not promise
  unattended stopping from a prompt alone or create another runner to compensate.
- Keep one continuation owner. Do not combine native goal, a chat timer and an external cron for
  the same state. A goal launch can replace an existing objective; expose that conflict first.
- Before resuming, reconcile exact session, repo/worktree, original goal and contract version,
  state/cursor, cumulative counters, run handle/generation/owner, cancellation and surviving work.
  Do not reset state or resend an uncertain external effect. One writer; preserve unknown locks.
- A local/worktree scheduled task needs accessible saved files in that execution context. Desktop
  local tasks need the host/app available. Web scheduled tasks cannot read a local folder simply
  because its path appears in a prompt. CLI/IDE alone do not provide Scheduled management UI.
- Only offer a runnable schedule setup when the tool/surface and required files are reachable.
  Explain where results appear and what is not yet configured. Do not create it from a request
  merely to generate a loop. Explicit authorization in the same request is sufficient; do not
  invent a mandatory second request, but do not expand this generator into a runner.
- Budget exhaustion is an incomplete checkpoint, not success. Keep required native status
  transitions separate from observed blockers; do not manufacture turns to satisfy thresholds.
  Record impediments immediately, attempt necessary authorized recovery, continue independent
  authorized work, and report unsupported
  capabilities honestly. Native completion/evaluation never substitutes for criterion evidence.
