# Purpose-led choices and copyable output

Use this guide in Steps 2 and 6. Generate contracts; do not start project work.
The entrypoint SKILL.md Final output contract is the presentation source of truth; this guide
provides purpose/readiness and copy hygiene, not exceptions to that contract.

## Choose the purpose before the mechanism

When the purpose is unclear, offer only meaningful concrete, project-grounded goals: for example, repair
the current failing suite, finish the next milestone, or watch for new CI failures. Explain
what each includes and excludes. A watcher is not a substitute for repairing today's failure.
Do not create executable contracts or initialize state for unselected purposes. Wait for the
purpose choice when material; minimal-interaction requests may use the stated closed
interpretation with internal progress checkpoints. If the request explicitly asks to compare, preserve the comparison.

When the purpose is clear, derive the requested usable/delivered result and its necessary work
before choosing the mechanism. Explain what currently works, which evidenced gaps remain, how the
actor will discover further necessary in-scope work, and what proves the delivered result. The
initial task list and suite are not exhaustive. Do not invent work merely to fill the contract.
Recommend the simplest available way to carry that same job through. For closed completion,
select modes using the entrypoint Final output contract; for other purposes show only useful ready choices. Each explains its suitability, actual work, stopping and resume. Goal/no-Goal
changes continuation machinery, not the required result or quality. Ordinary execution can pursue
successive useful steps now; it is not automatically one iteration or configured cross-turn
continuation. Reserve a one-pass limit for an explicitly selected bounded pass. Do not add a manual
single pass or a watcher just to fill a menu or silently shrink the requested completion.
Explicit runtime, cap, gate and safety decisions override defaults without a second confirmation.
For a closed completion request on either host, include the available Goal-equipped version in the
initial proposal; recommend it for requested looping/cross-turn continuation. Apply the current
host guide's lifecycle binding before judging readiness. Explicit no-Goal/bounded choices
and actual capability/ownership/limit constraints still override this default.
When both modes are ready, use the entrypoint default Goal/ordinary pair unless its explicit
exclusive-mode exceptions apply. A request to use Goal alone is not a request to show Goal only. Both bind the
same outcome/state and REMEDIATION SCOPE, not two different projects or a mandatory single pass.
Explain that necessary authorized blocker repair is included in both; a repaired prerequisite
returns to the original work without a fresh user request. Genuine native/runtime boundaries
remain, and this contract is not an automatic resume service. Do not add irrelevant menu choices.
When a requested runtime is confirmed available, it is the selected/recommended mode, not merely
an alternative. In particular, a CI/external-resume request must not silently become manual-first;
manual can be an optional inspection card, not a replacement recommendation. If the requested mode
is unavailable, keep it recorded as requested/unconfigured and explain the usable alternative.
An unavailable continuation is not consent to downgrade to a single iteration. Keep the user's
completion intent even when the goal backend is blocked or exposes no resume/active control.
Describe a single pass only as a different, optional mode; do not select or launch it on the
user's behalf. If no confirmed mode implements the requested continuation, explain that gap
without a runnable replacement block. Do not invent a resume control or a configured runner.

## Preserve meaning before shortening

Read the existing contract and state before reissuing a compact launch. Save the original goal,
all residual requirements, requested execution/continuation mode, acceptance and stop conditions,
consumed/remaining cumulative budget with its source and enforcement, authorization and forbidden scope, consultation/review
requirements, and exact state/resume ownership in the contract. Omitted launch details must be
present there, not left in old conversation or silently dropped. Compare the short launch against
these obligations; shortening is not permission to replace completion with "one iteration".

Classify counts before judging runway. Record each value/unit, source (user/platform/agent-default),
evidence and enforcement in the normalized saved contract and state. An explicit user cap of 8
with 7 consumed leaves one authorized attempt; an agent-default checkpoint at 8 does not exhaust
user authority. At that checkpoint review progress/failure signatures and replan internally,
keeping the cumulative ledger. Do not ask for another 8 merely to extend an internal horizon.
Unknown provenance calls for reading original instructions/state, not guessing. Actual cost/time
and scope boundaries still apply; this is not unlimited-spend authorization.
Budget consumption and runtime availability are separate facts. Do not reset counters or call the
work configured/started to make it look usable. Historical 7/8 input cannot rewind live 8/8 state.

## Resolve readiness inside the invocation, before presenting a launch

Produce a coherent saved artifact and its launch, not a plausible command followed by reasons it
cannot run. Before final output, reconcile the actual request, saved contract, current state and
remaining budget, live run ownership, and the exposed host's start/resume/stop controls. A normal
chat sentence saying "continue until complete" does not configure native cross-turn continuation.
Do not use that sentence to disguise a blocked backend or a missing resume operation.
Readiness concerns the launch's prerequisites, not whether it has already been launched.
A fresh Goal with confirmed target start/lifecycle controls is not a blocked existing Goal. Resolve
its completion, actual blocker handling and any explicitly requested pause in the saved contract
during generation. "Stop conditions still need connecting" is unfinished assembly, not a reason
to omit the Goal launch. Do not introduce a pause requirement the user never supplied.

If a material user decision is needed, bundle the concrete unresolved choices once during the
skill invocation: state the observed budget/control/ownership facts and exactly what authority
or mode change would be needed. Do not ask for facts already readable or for extra budget when
that alone cannot resolve a known capability failure. After an answer, finish contract assembly,
save/read-back and presentation in the same workflow; do not hand back a half-prepared launch.
Bundling once does not mean assuming an unanswered choice or ignoring a newly discovered
material gap: keep awaiting-decision status until it is resolved. User/platform limits remain
binding; changing an actual user limit needs explicit approval and cannot bypass a native limit.
Replanning an internal checkpoint needs no extra-budget ritual and must preserve history.

Before any copy fence, distinguish: (1) an executable proposal for the requested mode, verified
against its actual prerequisites but not yet started; (2) a proposal awaiting a specified user
decision, with no executable block yet; or (3) a capability/budget/ownership constraint for which
**no executable launch for the requested mode has been generated**. For (3), keep the original
intent and saved state, explain what is missing and omit all replacement launch blocks. Do not
present a command and then retract its usability in a later caveat or follow-up turn.

With agent-default 8/8, working continuation controls, no owner conflict and approved scope,
produce a ready continuation proposal after internal replanning; do not suppress it solely on count.
With an exhausted user/platform hard limit, omit launches for new work until a legitimate change
resolves it. With blocked Goal and no usable required resume control, outcome (3) follows from the
technical constraint even if 8 was only internal. Neither a budget question nor a chat sentence
repairs that control. A documented but uninspected capability is unknown, not proven absent;
inspect available read-only controls before deciding. Existing-result reconciliation/checkpointing
is distinct from new work. Re-generation must not reset the ledger. Re-read saved files before final
presentation and verify that purpose, residual work, mode, limits, authority, review and ownership
still match; a structurally short block alone cannot establish this semantic agreement.

For ready proposals only, use stable A/B/C labels in the explanations and final copy blocks. Put the single recommended
choice first in both places; honor an explicit supported runtime. Default to the active host only,
not a mixed CC/Codex menu. Different modes are alternatives, not steps to execute in sequence.
State before the copy group that only one may own the saved state at a time.

## Explain choices briefly; keep operating details in Markdown

Save the full purpose, scope/effects, use/delivery path, criterion/evidence map, recovery authority,
verification budget, actual limits, host lifecycle and resume procedures in the Loop Markdown.
Retain meaningful mode differences there too. Chat is a compact delivery wrapper, not a second
contract: normally one outcome sentence, one saved-path/readiness line, and one choice-distinction
line when there are alternatives. Explain only the differences the user needs to select a mode.
Do not repeat per-iteration rules, inventories or the same stop/budget/state details for every card.
Keep real unresolved high-impact choices, unusual effects and material capability gaps visible;
brevity must not hide something needed to choose or run the proposed action.
This replaces the earlier long candidate-card checklist in chat, not its saved-contract content.

## Final-only output: explanation, contract, launches last

Do not show launch commands or the full Loop body in commentary, progress messages, proposals,
question rounds or before saving/checking is complete. Explain purpose choices when needed, but
hold executable text until the final deliverable. Inline feature names are fine; concrete
launches with the saved paths are not, even without a code fence. The user must not have to hunt through the
conversation to find the latest launch. Earlier copy-first guidance is superseded by this rule.

After resolving material questions, saving files and completing assembly checks, use the
entrypoint Final output contract on either host. Briefly name any user-requested pause on the
status line; do not invent one. For selected handoff, keep its exact state location in the saved
contract. Show the full checked contract only on explicit request, before the paste group,
using a longer outer fence if needed; never reconstruct another version or show an unchosen
purpose's executable contract.

Before the final group, use one short instruction: **Copy one whole code block to the named input;
the explanation and saved path are not to paste.** With alternatives, say to choose only one and
not run concurrent writers. Do not repeat long operating rules inside the launch: point to the
exact saved contract, keep the selected mode, and retain only context or native syntax/stop criteria
the actual host needs outside that file. A short launch must preserve the full outcome and actual
limits/authority in the referenced contract. Neither hidden detail nor a normal message invents
native continuation or a missing resume control.

If no confirmed execution mode matches the explicit request, omit the launch group and report
the requested mode as unconfigured; do not manufacture a recommended single pass.

After the last launch fence, output nothing: no summary, warning, file links, cost note, question,
metrics or repeated assumptions. Do not repeat a launch under its earlier candidate explanation.
Long criteria/source inventories remain in the saved contract. Displaying a path or an explicitly
requested body does not authorize executing it or creating schedules.

## Copy contract

- One independently usable launch per fenced `text` block (conversation input) or `sh` block
  (terminal). Label the host, destination and execution unit immediately outside the fence.
- A bare lifecycle control such as `/goal resume` is not a task-bound execution prompt. Put such
  controls in the earlier lifecycle explanation, not as the sole final answer to a request for a
  Loop prompt. A runnable resume proposal must bind the correct existing task/contract and target
  worktree/session, preserving state and using only supported controls. A missing resume capability
  remains a real readiness gap; a longer normal message cannot manufacture it.
- Inside: only what to paste. No bullets, shell `$` prompt, wrapping display quotes, explanatory
  comments, other candidates or mixed shell/chat commands. Preserve syntactically required quotes,
  including around shell paths with spaces. Use the user's language, not smart-quote shell syntax.
- Make each block self-contained through its exact saved contract path and execution unit
  (one iteration/tick, goal continuation, schedule setup or exact-session execution). Bind the
  state/cursor, limits, pause rules and authority in that file; do not repeat them all in the
  launch. Never rely on “same as above” or a previous chat block. An explicitly selected bounded
  pass returns after its unit; ordinary no-Goal execution need not. Neither may clear a user pause
  or override an active continuation owner.
- Keep launches short, normally one physical line referencing the saved contract. A single long
  line is not a copy-safety fix: selection can turn visual wrapping into real newlines. Never
  insert a newline inside a filename, path, quoted argument or identifier, and do not claim that
  a code fence prevents copy corruption. Put explanations outside the copy block.
- For new files prefer short, meaningful slugs such as `ui`, `auth` or `ci`; use project-relative
  paths such as `.loop/ui.md`, not absolute paths or descriptive sentence-length filenames.
  Preserve existing names and state during refine. If an existing path makes the launch too long,
  offer a scope-limited rename with all references updated and state preserved; do not silently
  rename it, reset its state, or create a second contract/runner merely for a short alias.
- Only for a user-selected single pass, with scope and limits bound in `.loop/ui.md`, a compact
  manual message can be `.loop/ui.md に従い1回進めて。`. Never reuse that example to shorten an
  existing continuation request. For a confirmed continuous mode, reference the contract with
  that mode's native launch and preserve its stop semantics. This is not a fixed filename or a guarantee of
  fitting every pane. Use the actual saved path and host-native syntax. Check that the launch
  resolves to that file and contains no path-internal newline; visual clipboard fidelity remains
  unverified unless actually observed on the target surface.
- Resolve actual slug, paths, interval and session ID. Do not emit runnable placeholders.
- A capability documented but unconfirmed/unavailable in this session belongs in a separate
  **Conditional options** explanation, not an executable copy fence. Offer a verified alternative.
- A conversation block is not a shell command: do not wrap it in `claude -p` or `codex exec`.
  A terminal block contains only shell syntax with real quoting (including apostrophes in paths
  or prompts). Do not add permission-bypass flags for convenience. Never combine launch and
  separate pause/clear/resume command strings in one block. Keep lifecycle guidance in the earlier
  explanation; a task-bound resume instruction is not a bundle of unrelated lifecycle commands.
- For schedule setup, label **creates a schedule**, not “starts one tick”. Generating its setup
  message does not create it. Do not create a runner or schedule without explicit authorization.
- Two launch alternatives can reference the same contract/state, but only one may write it at a
  time. Explain switching after the earlier run has stopped; never suggest concurrent launches.
- Do not overwrite existing state/cursor, choose a purpose, set an INDEX selection or replace an
  active native goal merely because alternatives were displayed.

## Example differences (not fixed presets)

“Finish the repair” keeps pursuing the accepted failing-case criteria using native continuation.
“Try one iteration” uses the same criteria/state but returns control after one bounded iteration;
it can include an edit and is not a read-only diagnosis. It reports remaining work, not fake success.
“Watch new CI failures” is a different open purpose, with new-event dedup and an explicit reaction
boundary; it does not fix current failures unless authorized. Derive actual cards from the request.
